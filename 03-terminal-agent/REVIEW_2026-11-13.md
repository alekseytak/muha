# Разбор terminal-agent и L0–L5, 13 ноября 2026

## Короткий вывод

Не нужен ещё один уровень архитектуры. Сейчас смешиваются три разных вопроса: что пользователь просит, можно ли это делать и получилось ли выполнить задачу. Надёжный следующий шаг: завершённый контракт действия и проверка реального результата на небольшом независимом наборе. Расширять таксономию пока рано.

Проверены указанные core/hierarchy.py, eval/hierarchical.py, eval/robustness.py, core/micromodels.py, ключевые пути core/agent.py, тесты иерархии и каскада tests/test_agent.py, весь раздел 25 AUDIT.md и раздел L0–L5 ARCHITECTURE.md. Дополнительно проверены GateKeeper, VerbAct, исполнители инструментов и AutonomousRunner. Весь набор из 132 тестов исполнен. Это не полный аудит научного коннектомного подпроекта.

Исходники не изменялись. Реальные LLM и API не вызывались. Опасные фразы только разбирались, не исполнялись. Тестовый runner выполнял собственные тесты с временными песочницами и локальными stub-серверами.

## Подтверждённые проблемы по приоритету

### 1. Правила ищут слова, но не устанавливают намерение пользователя

`core/micromodels.py:161–197`, затем `core/hierarchy.py:125–138`.

На боевом `Agent.propose_action_fast`:

| Фраза | Полученный акт | Что важно |
|---|---|---|
| не запускай команду date | execute sys:date | Gate ALLOW, но инструмент ещё требует подтверждения |
| посоветуй как выполнить команду date | execute sys:date | Совет ошибочно превращается в команду |
| прочитай файл anchor.md | anchor, domain registry | В текущей конфигурации Gate DENY, то есть это не доказательство выполненного anchor |
| закрепи вкладку браузера | anchor | Любое «закрепи» принимается за канонизацию |
| расскажи что означает вето | veto | Упоминание действия принимается за требование его совершить |

Нельзя лечить это бесконечным добавлением отдельных regex на каждую найденную фразу. Нужна консервативная граница: отрицание, цитата, вопрос о действии, смешанное намерение и несколько действий должны вызывать воздержание локального роутера. Это инженерная политика кандидата, а не автоматическое разрешение действия даже после fallback в LLM.

### 2. Классификация глагола не равна готовому действию

`core/micromodels.py:262–285`, `core/agent.py:350–352`.

Подтверждено:

- «запусти команду uname -a» становится `sys:uname`, аргумент `-a` потерян.
- «запусти команду echo привет» становится `sys:echo`, текст потерян.
- «запиши в notes.md строку готово» становится write с пустыми parameters. Исполнитель fs.write требует content.
- «выбери одно из двух: A или B» становится select с пустыми parameters. ui.select требует options.
- «прочитай notes.md и запиши копию в backup.md» сворачивается в один read, второе действие молча исчезает.

Сначала определить обязательные поля поддерживаемого инструмента. Если локальный путь их не собрал достоверно, он должен воздержаться, а не объявлять разбор успешным. Команды надо разбирать с сохранением argv и проверять существующим sandbox, не включать shell. Не обязательно писать новый фреймворк: начать с уже имеющегося ToolSpec и одной общей проверки на границе готовности кандидата.

### 3. Замер не подтверждает пользу модели иерархии

Воспроизведено `../.venv/bin/python eval/hierarchical.py`:

- Flat: 140/152, глагол 0.986.
- Hierarchical: 152/152, глагол 0.987.
- Источник ВСЕХ 152 решений иерархии: `μ1a`. Ветка μL/μV использована 0 раз.
- Дополнительные 12 ответов: veto/escalate, которые flat намеренно отправляет наверх через μ3.

Это реальное расширение локальной политики для контрольных глаголов, но не свидетельство улучшения за счёт обучения уровней. Для проверки именно иерархии нужен одинаковый policy baseline и отдельная абляция статистической ветки на фразах без правил. Нельзя приписывать весь эффект L0–L5.

Модель в живом Agent обучается на 39 фразах `eval/cases.json`, а опубликованный эксперимент на 177 фразах `cases_distill.json`. Это разные конфигурации, результаты нельзя автоматически переносить.

На имеющихся метках `selective_report` даёт для иерархии на 152 фразах:

- глагол 150/152 = 98.7%;
- домен 133/152 = 87.5%;
- глагол И домен 132/152 = 86.8%.

Метки доменов местами явно подозрительны, например anchor помечен как connectome. Поэтому 86.8% не объявляется истинной пользовательской точностью. Но игнорировать домен нельзя: надо вручную проверить маленький независимый gold-набор, а не называть один лишь глагол точностью действия.

Боевой каскад на `cases_holdout.json`: покрытие 22/25, глагол 20/22 = 90.9%, глагол+домен 19/22 = 86.4%. Это также имеющиеся метки, не независимая приёмка.

### 4. Обещание «L4 без улики не бывает» реализовано частично

`core/hierarchy.py:152–170`: запрет на статистический L4 стоит только внутри `len(options) == 1`. Когда в L4 есть и veto, и escalate, выполнение идёт по ветке статистики.

Воспроизведено с обучением на 177 фразах: «оператор необходим» -> escalate, источник `μL/μV (L4)`, уверенность 0.7095. Явного правила нет. Это может быть разумной эскалацией, но противоречит строгой формулировке теста и документации. Нужно выбрать одну политику: либо L4 только по явной улике для всех размеров options, либо разрешён статистический L4 с явно описанными рисками. L5 с единственным anchor сейчас воздерживается без правила.

### 5. Два слоя определяют разные домены

`core/agent.py:358–359` подставляет domain классификатора. `core/gatekeeper.py:75–76` заново выводит domain из object, а исполнитель использует domain акта. Например непомеченный объект anchor получает registry у каскада, но ui в проверке грамматики. Сейчас это часто приводит к отказу, не к повышению прав, однако policy и dispatch должны проверять одну и ту же каноническую пару verb/domain.

Не исправлять простым «пусть гейт верит модели». Канонизация и валидация целевого инструмента должны произойти до проверки прав.

### 6. L0–L5 не являются универсальной шкалой риска

Таблица полезна как тип действия. Но рекомендация L3 не обязательно опаснее записи L2, а execute L2 может быть опаснее anchor L5. Нельзя разрешать действие условием `уровень <= полномочия`. Реальная проверка должна оставаться по субъекту, инструменту, объекту и параметрам.

`swarm.veto` и `swarm.escalate` сейчас кладут феромон, но сами по себе не отменяют будущую запись и не доставляют запрос человеку. Это полезная метка в симуляции, не завершённая операция контроля. Следует отличать «эскалация зарегистрирована» от «человек уведомлён».

### 7. Измерения и воспроизводимость

- В hierarchical.py bootstrap перевыбирает отдельные фразы, хотя фразы внутри шаблонных семейств зависимы. Для переноса на новые семейства уместнее cluster bootstrap по family. Текущий CI не доказывает 95% надёжность в открытом мире.
- Правила дорабатывались после чтения результатов этой отложенной выборки. Это полезный regression-набор, но уже не нетронутый final holdout.
- `eval/robustness.py main()` в третьей части вызывает внешнюю модель. В этом разборе запущены ТОЛЬКО локальные learning_curve и cascade_ci. Полный robustness не запускался.
- В hierarchical.py список extra включает все отказы flat, до фильтрации None у hier. При нынешнем результате все дополнительные ответы есть, но при другом наборе напечатанное число может завышать число новых решений.
- `VerbMicroModel.fit` очищает counts/totals/priors, но не vocab. Подтверждено: после переобучения на xyz слово из первого корпуса остаётся знакомым с known_ratio=1.0. Это небольшой самостоятельный баг, не причина всех ошибок.
- Заголовок hierarchy.py и комментарий agent.py ещё содержат старые 96%/0.993 и 146/146, тогда как последние документы говорят о 100%/0.987.

## Как выйти из текущего тупика

На один цикл разработки заморозить новые уровни, модели и пороги.

1. Сохранить нынешний работающий путь как baseline, не выбрасывать проделанную работу.
2. Сделать небольшой отдельный набор независимых проверок: отрицания, цитаты, названия файлов с глаголами, аргументы команд, несколько действий, отсутствующие параметры. Ожидаемый исход включает abstain, а не обязательный ответ на всё.
3. Исправить только границу «кандидат готов к исполнению»: намерение, точный объект, обязательные параметры. Неполное решение отправляется на разбор, а не исполняется частично.
4. Проверить полный сценарий propose -> canonicalize -> gate -> confirmation -> tool -> проверка результата -> registry. Для read ожидается точное чтение нужного временного файла. Для write точные байты. Для запрета отсутствие действия. Для argv полный согласованный вызов в тестовом backend.
5. Лишь после этого сравнить flat и hierarchy при одинаковых правилах и policy. Решить, нужна ли статистическая иерархия по измерениям, а не по названию.

Критерий завершения ближайшего шага: ни одно отрицание или объяснение не запускает действие; ни одна команда не теряет argv; неполные write/select не объявляются готовыми; гейт и исполнитель проверяют один и тот же инструмент; обычное чтение сохраняет быстрый локальный путь.

## Один вопрос Алексею

Что сейчас должно быть главным результатом МУХА?

1. Практический локальный помощник для файлов, сайтов и команд.
2. Исследовательская платформа для проверки роутинга и глагольной архитектуры.
3. Агент, в котором поведение реально определяется обучаемым коннектомом/SNN.

Моя рекомендация на ближайший цикл: вариант 1 как проверяемый инженерный минимум, при этом вариант 3 вести отдельным экспериментальным контуром. Сейчас terminal-agent использует коннектом в основном как источник читаемых данных, а каскад классифицирует фразы regex/NB. Это не один и тот же эксперимент, и объединять их метрики нельзя.
