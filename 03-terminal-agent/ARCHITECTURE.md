## Поток принятия решения

1. Пользователь вводит текст в терминале.
2. LLM превращает его в VerbAct: `ГЛАГОЛ: объект | {параметры}`
   (принимается и JSON `{"verb":…}`, и русские глаголы, и ответ в ```-блоке).
3. Домен определяется по префиксу объекта (`file:`, `sys:`, `connectome:`, …).
4. GateKeeper проверяет пару (домен, глагол) и права роли → ALLOW / DENY / ESCALATE.
5. Для инструментов с `requires_confirmation` спрашивается подтверждение
   (политика `gatekeeper.confirm`: ask | allow | deny).
6. Инструмент из `tools/registry.py` выполняет реальную работу.
7. Registry записывает след: глагол, объект, домен, имя инструмента, длительность,
   успех/провал (append-only, SHA256-цепь).
8. Гормоны обновляются: успех → дофамин, провал → кортизол.
9. Голоса роя могут канонизировать «золотое яблоко» (≥66 %, ≥3 голосующих).

## Модель LLM

Поддерживаются два протокола (`core/llm_client.py`):

| provider      | protocol            | endpoint                          |
|---------------|---------------------|-----------------------------------|
| oneprovider   | [OI]-совместимый    | `{base_url}/chat/completions`     |
| literouter    | [OI]-совместимый    | `{base_url}/chat/completions`     |
| openrouter    | [OI]-совместимый    | `{base_url}/chat/completions`     |
| ollama        | нативный            | `{base_url}/api/chat`             |

Ключ берётся из переменной окружения (`llm.api_key_env`), затем из YAML-файла
`llm.credentials_file` (формат `VAR_NAME: value`). В `config.yaml` ключей нет.

Если основной провайдер недоступен, `think()` пробует `llm.fallback`
(по умолчанию локальная Ollama), а при полном отказе возвращает
`[Ошибка LLM: …]` — такая запись попадает в реестр с `success=false`.

Инструменты доменов `registry` и `swarm` меняют настоящее состояние:
`registry.log`/`registry.anchor` пишут запись в append-only цепь и возвращают

`ui.recommend` считает рекомендацию по гормонам и последним записям реестра.

замена реестра агентом сразу видна инструментам.

### Модель безопасности файлов

`modules/filesystem.py` работает внутри `tools.filesystem_root`. Любой путь,
выходящий за корень (в том числе через `..` и симлинки), отвергается.
Запись атомарная (temp-файл + `os.replace`), лимиты на чтение и запись.

### Модель безопасности команд

`modules/system.py` — два бэкенда запуска (`tools.commands_backend`):

* `posix` (по умолчанию): `os.fork` + `os.execvp` + неблокирующие pipe.
  Не импортирует `subprocess`, поэтому работает даже там, где загрузка
  `_posixsubprocess` зависает в `dlopen`;
* `subprocess`: обычный `subprocess.run`, если он доступен.

Общее для обоих:
* `shell=False`, разбор через `shlex` — шелл не участвует;
* первое слово обязано быть в `tools.allowed_commands`;
* подстроки из `tools.denied_patterns` режутся до запуска;
* метасимволы `; | & $ \` < >` запрещены;
* таймаут `tools.command_timeout` (на бэкенде `posix` — `os.kill(pid, 9)`), вывод обрезается;
* код возврата ≠ 0 — провал инструмента (`success=false` в реестре).

# Обновления второго захода (2026-11-13)

## Режимы работы

`agent.mode` в конфиге управляет тем, что агенту позволено, и проверяется
в `Agent.execute` **до** гейта:

```
execute -> режим (_mode_block) -> гейт (GateKeeper) -> подтверждение -> инструмент -> реестр
```

* `interactive` — по умолчанию, опасные действия спрашивают подтверждение;
* `read-only` — запрещены `write/execute/anchor/veto`; `log` разрешён (аудит);
* `autonomous` — всё, что требует подтверждения, запрещается: спрашивать некого.

Смена режима — `Agent.set_mode()` или команда `mode <имя>` в CLI.
Отказ режима попадает в реестр с `metadata.mode`.

## Привилегии команд

`tools.allowed_commands` — наблюдательные команды. `tools.privileged_commands`
(`python3`, `git`, `bash`, `sh`, `node`, …) дают исполнение произвольного кода,
поэтому разрешены только ролям из `tools.privileged_roles`. Роль доходит до
песочницы через `ToolContext.role`:

```
Agent.role -> ToolContext.role -> run_command(..., role=...) -> SystemSandbox.check(command, role)
```

## Автономный режим (третий заход)

Режим `autonomous` — это не «агент без ограничений», а цикл, который сам
выбирает следующий шаг, но проходит **тот же путь**, что и интерактив:
режим → гейт → подтверждение (или предодобрение) → инструмент → реестр.

```
task add <текст>            очередь задач (memory/tasks.jsonl, append-only)
      |
      v
Agent.run_autonomous()      бюджеты из config: autonomous.*
      |
      v
AutonomousRunner.run_task() цикл шагов
      |
      +-- build_prompt()     задача + история + наставление (nudge)
      +-- agent.think()      ОДИН вызов модели на шаг
      +-- agent.execute()    обычный путь: режим, гейт, реестр
      |
      +-- стоп-условия: THINK=решено | max_steps | бюджет вызовов |
      |                 повтор действия | две ошибки подряд |
      |                 два ответа не в формате
      v
RunReport + queue.close()   задача закрывается ОДИН раз, в конце
```

### Деньги

Главная статья расхода — системный промпт на каждом шаге: 2630 символов
(≈876 токенов) при полезной нагрузке шага в 100–200 токенов. Поэтому:

* бюджет — в **вызовах модели**, и проверяется ДО запроса, а не после;
* `LLMClient` считает реальные `usage` от провайдера (`usage_report()`),
  а не оценку по символам; если провайдер расход не сообщил, это видно
  в `calls_without_usage`, и `RunReport.tokens_reported = False`;
* компактный промпт (790 символов, −70%) **выключен по умолчанию**: замер
  на контрольной выборке дал 60% точности разбора глаголов против 100%
  с полным промптом. Экономить надо числом шагов, а не качеством разбора;
* на прогон ставится `temperature = 0` (и возвращается обратно): разбор
  глаголов должен быть воспроизводимым.

### Предодобрение

Действия, требующие подтверждения (`write`, `execute`, `anchor`, `veto`),
в автономном режиме **запрещены**, пока оператор не включил
`autonomous.pre_approved: true`. Это отдельный ключ, а не следствие
`gatekeeper.confirm`: тот отвечает на вопрос «спрашивать ли», а не
«можно ли действовать без человека». Выполненное по предодобрению действие
помечается в реестре `auto_approved: true`, чтобы его нельзя было спутать
с подтверждённым вживую.

### Честность отчёта

Отдельный дефект, найденный на живом прогоне: когда модель отвечала не по
формату, парсер подставлял `THINK` с текстом **своего же промпта**, и цикл
закрывал задачу как решённую. Теперь такой разбор помечается константой
`FORMAT_FAILURE`, шаг считается провальным, модели даётся одно наставление,
а второй промах закрывает задачу как `failed`. Итог задачи берётся из
последнего успешного `THINK` (`RunReport.final_answer`), а не из причины
остановки.

## Чтение веба (Scrapling + Obscura)

Домен `web` — «глаза» агента. Загрузка и разбор разделены, чтобы не тащить
в терминальный агент браузер:

```
web:<url> / url:<url> / http(s)://…
        |
        v
WebFetcher.fetch()          urllib + build_ssl_context (бандл macOS неполный)
        |                   SSRF-фильтр: только http/https, никаких localhost,
        |                   10/8, 192.168/16, 169.254.169.254 и .local
        v
html_to_text()              Scrapling Adaptor: блоки (h1..h6, p, li, pre, td)
        |                   -> абзацы; script/style/nav выброшены
        v
read_web() / page_info()    текст с шапкой (URL, HTTP, тип, размер, селектор)
```

* `pip install scrapling` — **только парсер**, без `[fetchers]` и без
  `scrapling install`, то есть без ~300 МБ Chromium. Проверено: 0.5.1,
  `lxml` подтягивается сам.
* Без Scrapling модуль продолжает работать на регэксп-фолбэке и честно
  пишет в шапке `разбор: fallback` + `ВНИМАНИЕ: …` — деградация видна.
* Инструменты: `web.read` (READ) и `web.info` (SELECT). Всего инструментов 15.
* Объект достаёт μ1c: URL из фразы, путь с расширением, известная команда.
  Если для домена `web/filesystem/system` объекта нет — каскад воздерживается,
  а не подставляет всю фразу.

**Obscura** (`~/obscura-x86_64-macos/obscura`) — второй путь, когда нужен
настоящий браузер и JS: `obscura fetch --dump text|markdown|links <url>`.
Проверено: отдаёт текст отрендеренной страницы. Пока не подключён к агенту —
это следующий шаг, а не сделанное.

## Микромодели действий: μ1 → μ2 → μ3 → омега

Идея: глагол — это выбор из одиннадцати, а не генерация текста, который мы
потом парсим обратно. Поэтому дешёвая модель может решать сама, а большая
зовётся только там, где дешёвая **честно воздержалась**.

```
фраза
  |
  μ1a  правила высокой точности (CUE_RULES)        уверенность 0.9
  μ1b  наивный Байес по символьным 3-граммам       + запас над вторым
  μ1c  извлечение объекта: URL / путь / команда
  μ2   домен: префикс объекта, затем лексика (границы слов)
  μ3   рой/эскалация: такие случаи всегда отдаём омеге
  |
  +-- уверены -> VerbAct без вызова модели
  +-- нет     -> омега (большая модель), обычный путь
```

Воздержание — не отказ, а маршрутизация. Каскад молчит, если:

* размеченных примеров меньше `MIN_TRAINING_EXAMPLES = 8`;
* в обучении меньше двух глаголов (один класс ничего не различает);
* знакомых n-грамм меньше `KNOWN_GRAMS_FLOOR = 0.3` (фраза незнакома);
* запас над вторым кандидатом меньше `MARGIN_FLOOR = 0.15`;
* для `web/filesystem/system` не найден объект;
* случай похож на эскалацию (μ3).

Все пороги — в `core/micromodels.py`, включаются и выключаются блоком
`micromodels:` в `config.yaml`. Статистика (`decided`/`escalated`) видна в
`agent.stats()["micromodels"]`.

## Браузерный рендер: Obscura

Scrapling разбирает HTML, но не исполняет JS. Для страниц-каркасов (SPA)
домен `web` пробует настоящий браузер:

```
urllib  ->  html  ->  Scrapling  ->  текст
                               |
              мало текста при большом HTML (каркас)?
                               v
            Obscura (os.posix_spawn, без shell) -> текст после JS
```

* `modules/browser.py` запускает **внешний бинарь** через `os.posix_spawn`
  с argv-списком: подстановка аргументов невозможна, shell не участвует.
  `subprocess` сознательно не используется — в этом окружении он виснет.
* Окружение урезано до `PATH/HOME/TMPDIR/LANG/LC_ALL`: браузеру не нужны
  наши секреты.
* Дедлайн жёсткий: по истечении бинарь получает `SIGKILL`, вызывающий —
  `BrowserUnavailable`. Вывод ограничен 4 МБ.
* Эвристика включения: `текста < 400 символов` **и** (`HTML > текста × 20`
  **или** страница просит включить JavaScript). Короткая страница-визитка
  под это не подпадает — она читается без браузера.
* Кто именно читал — всегда в шапке ответа: `разбор: obscura (после JS)`
  и `браузер: obscura, за N байт`. Молчаливой подмены нет.
* Браузер отклоняет приватные адреса **сам** (проверено: отказ на
  127.0.0.1), независимо от нашей SSRF-проверки — две независимые защиты.

## Оценка вариантов через вероятности (logprobs)

Вместо «попросить модель написать глагол и разобрать строку» — прочитать
распределение, с которым модель готова выдать каждый из одиннадцати глаголов.
Решение становится argmax по вероятностям с честным запасом.

```
фраза -> OpenRouter (provider.require_parameters=true) ->
         logprobs.top_logprobs (20 токенов) ->
         канонизация токенов (« read», «read\n» == read) ->
         суммирование вероятностей одного варианта ->
         нормировка на массу вариантов -> best, запас, доля массы
```

Что выяснено замерами (AUDIT.md, раздел 24):

* `oneprovider` **молча игнорирует** `logprobs` — вернул `null`, при `logprobs: true`.
* OpenRouter отдаёт распределение, но **только** у провайдера, который его
  поддерживает: без `require_parameters` тот же запрос вернул `null`.
* `mistralai/mistral-nemo` (DekaLLM) отдал `read 0.819 / write 0.001` — это и
  есть перенос идеи SemIf на доступный API без GPU.

Ловушка нормировки: `mass_on_options` — доля **показанной** массы, пришедшаяся
на варианты. Низкая доля значит «модель отвечает не из списка», и это сигнал
не доверять выбору. Вероятности нормируются на массу вариантов, поэтому
`mass` нельзя читать как «уверенность» — для этого есть запас `margin`.

## Иерархия уровней L0–L5 (взята из архива КЭМ)

Источник — `OS-Glagolov-spec.md:41-49`, цитируется в
`ГЛАВНАЯ ПАПКА/ОС_глаголов_система.md`: шесть нормативных уровней действия.
Их смысл — не «частота», а **уровень полномочий**: чем выше, тем необратимее
действие.

| уровень | смысл | наши глаголы |
|---|---|---|
| L0 | Наблюдение | read, version |
| L1 | Анализ | think, select |
| L2 | Преобразование | write, execute, log |
| L3 | Рекомендация | recommend |
| L4 | Контроль | veto, escalate |
| L5 | Commit | anchor |

```
фраза
  |
  +-- есть улика в правилах? --> да --> глагол + домен + объект (μ1a)   [0 сети]
  |
  +-- нет --> уровень L0–L5 (μL) --> глагол внутри уровня (μV) --> домен (μ2)
                                   |
                        L4/L5 без улики --> отказ (нужна омега)
```

Три правила, каждое появилось из ошибки, а не из теории:

1. **Правила идут первыми.** Если спрашивать уровень первым, его ошибка
   выбрасывает верную улику правила: замер дал 68% покрытия и 0.495 точности.
2. **L4 и L5 не отвечают «по факту единственности».** «В обучении в этом
   уровне один глагол» — не доказательство. Для контроля и Commit нужна
   явная улика, иначе иерархия выдавала бы вето без оснований.
3. **Модель уровней обучается на своих метках.** `VerbMicroModel` по умолчанию
   фильтрует метки по списку глаголов, поэтому уровни L0–L5 молча
   отбрасывались все до одного. Теперь набор меток передаётся параметром.

Замер на 152 отложенных фразах (обучение на 177, семейства не пересекаются):

| каскад | покрытие | точность глагола | 95% CI |
|---|---|---|---|
| плоский (11 глаголов) | 92% (140/152) | 0.986 | [0.964, 1.000] |
| иерархия L0–L5 | **100% (152/152)** | 0.987 | [0.967, 1.000] |

Изменённых ответов на фразах, которые решал плоский каскад: **0**.
Добавлено 12 решений — все `veto`/`escalate` по явной улике («наложи вето на…»,
«запрети запись…», «позови человека…», «сообщи оператору…»), все верны.

Почему локальный ответ на `veto`/`escalate` безопасен: это отказ и передача
человеку. Худший случай ошибки — остановка работы или лишний вопрос, а не
необратимая запись. Обратный случай (`anchor`) без улики не выдаётся никогда.

## Границы, которые проверяются до действия (2026-11-14)

Раньше проверок было две: намерение и обязательные параметры. После разбора
80 фраз выяснилось, что этого мало: реализация исполнила действие в семи
случаях, где по смыслу его быть не должно. Каждая из проверок ниже появилась
из воспроизводимого случая, поэтому они перечислены вместе с ним.

| проверка | случай | что было до |
|---|---|---|
| отрицание по основам глаголов | «Не сохраняй ответ в notes.md» | выбиралось `log`, файл менялся |
| безличный запрет | «ничего не закрепляй» | выбирался `anchor`, писался реестр |
| местоимение без объекта | «Сделай с этим что-нибудь полезное» | выбирался `recommend` |
| цепочки оболочки (`;`, `\|`, `&&`, `$(`, обратная кавычка) | «Выполни echo first; echo second» | запускался `echo` с мусорным argv |
| последовательность («затем», «потом») | «Выполни pwd, затем uname -a» | запускался только `pwd` |
| глагол вне набора одиннадцати | «Сравни содержимое old.txt и new.txt» | статистика придумывала `write` |
| более одной цели действия | «Прочитай notes.md и запиши копию в backup.md» | выполнялось первое действие |
| наличие инструмента для пары глагол/домен | «Сохрани результат» | `write` с доменом `ui` проходил насквозь |
| побочный глагол требует улики правила | «Сравни содержимое…» | `write` угадан статистикой |
| дописывание нельзя подменять перезаписью | «Допиши в notes.md строку конец» | файл перезаписывался |

Два правила, без которых список выше бессмысленен:

1. **Проверка готовности идёт по домену акта, а не по домену каскада.** Раньше
   `write` из каскада получал домен `ui`, проверка записи не применялась, а акт
   потом канонизировался в `filesystem` с пустыми параметрами.
2. **Путь внутри единственной команды — её аргумент.** «wc -l notes.md» это одна
   команда, а не две цели: иначе счётчик целей отвергает законный запрос.

Порядок: улика правил → отрицание → оболочка → глагол вне набора →
местоимение → несколько действий или целей → наличие инструмента →
канонизация объекта → обязательные параметры. Отказ на любом шаге означает
воздержание fast-path и передачу омеге, а не «выполнить как поняли».

### Журнал реальных задач

`eval/real_tasks.py` прогоняет осмысленные задачи настоящими инструментами
(файлы, процессы, HTTP) и пишет партию в `eval/real_tasks_log.tsv`: запрос,
ожидание, наблюдаемый глагол, вердикт, артефакт и SHA-256 первых 16 hex.
Партии сравнимы между собой по дайджестам.

Что журнал показывает и чего не показывает:

* живая модель не вызывается; исход `LLM` означает «задача ушла бы модели»,
  и это не подтверждение её ответа;
* песочница временная, реестр отдельный, `confirm=allow`;
* ожидания в строках написаны агентом, это не человеческий gold;
* «прошло» относится к конкретной строке, а не к безопасности помощника.

Партия 1 (2026-11-14): 10 задач, 9 прошло, 1 наблюдение, 0 провалов.

## Демо: один прогон, который можно открыть

```sh
cd 03-terminal-agent/demo
python3 ../run.py --yes < input.txt     # настоящий CLI, песочница demo/sandbox
python3 build_demo.py                    # транскрипт + проверка артефактов
open SESSION.html                        # страница с результатом
```

Демо — отдельный конфиг `demo/config.yaml`: песочница `./sandbox`, реестр
`./registry.jsonl`, корпус обучения `../eval/cases_distill.json`. Конфиг
берётся из текущего каталога, поэтому прогон не трогает проект.

Что смотреть в `SESSION.html`: таблицу проверок артефактов (содержимое
записанного файла, неизменность нетронутого файла, число записей реестра,
цепь хешей) и сам транскрипт с источником каждого решения — `μ1a` для
правил, `text`/`llm` для омеги.

### Один корень для файлов и команд

`Agent.set_sandbox_root(path)` двигает и `fs_sandbox.root`, и
`system_sandbox.cwd`. Две песочницы легко расходятся: если двигать только
первую, файловые инструменты видят новый каталог, а процесс стартует в
старом, и `wc -l notes.md` отвечает `No such file`. Тесты и харнессы обязаны
пользоваться этим методом, а не присваивать `fs_sandbox.root` напрямую.

### Бюджет ответа модели

`llm.max_tokens: 2500`. При 512 рассуждающая модель тратила весь бюджет на
reasoning и возвращала пустой `content` с `finish_reason=length`; это
выглядело как «модель недоступна», хотя сеть и ключ были в порядке.
